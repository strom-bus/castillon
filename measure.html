Load measurement

Times an offline render with and without one unit of work. The difference is what that unit costs, divided by what a plain sine voice costs — which is already the unit audio/load.ts counts in, so a measured number can be dropped straight in.

This measures ratios, which transfer. It does not measure whether a hundred points is the right ceiling: that is about when a machine starts to struggle, and only listening answers it.

It also measures what sweeping a parameter adds to the thing being swept, which the budget prices at nothing today. Each of those is the same graph twice: once with a modulator connected to nothing, once with it connected, so the modulator's own cost cancels.

Takes a few minutes. Leave the tab in front — a background tab is throttled.

The ceiling is a different question on a different thread, so it is a separate run. The costs above come from timing an offline render — how fast audio can be produced when nothing is waiting for it. A ceiling is whether every block of 128 samples is ready in time, which only renderCapacity can answer and only in realtime. That run makes a quiet sound, on purpose: silence is something a browser may optimise away, and an optimised measurement measures nothing.

Find the ceiling plays real notes through the app's own engine and watches AudioContext.playbackStats for a dropout — so what it reports is the number the meter itself shows at the moment the audio thread first fails. No panel to read, no percentage to interpret. It needs Chrome 146 or later; if it is not there it says so, and the manual ramp below still works.
